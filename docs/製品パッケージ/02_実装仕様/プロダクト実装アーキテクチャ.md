# プロダクト実装アーキテクチャ

## 結論

実装言語は Python でよい。

理由は、既存コードが Python 中心であり、TSV/CSV/YAML/JSON の処理、LLM CLI/API 呼び出し、バッチ実行、監査、可視化用エクスポートとの相性がよいからである。

ただし、現状のコードはまだ「AGI時代の若者デモを動かすためのスクリプト群」であり、汎用プロダクト基盤としてはパッケージ境界とプロトコルを切る必要がある。

目指す状態:

```text
ドメインパックを差し替えるだけで、
企業、行政、学校、国家、地域などの施策反応・波及シミュレーションを
同じ実行基盤で回せる。
```

## 基本方針

このプロダクトは、自由すぎるLLMごっこではなく、制度設計・シナリオ予測に使える創発観測装置である。

そのため、次を分離する。

| 層 | 役割 |
|---|---|
| `sim_core` | 汎用実行基盤 |
| `domain_packs` | テーマ固有の入力セット |
| `model_adapters` | LLM/API/CLI/ルールベースの差し替え |
| `outputs/runs` | 実行結果、ログ、監査結果 |
| `visualization` | 再生UI、デモ表示 |
| `docs` | 設計思想、プロトコル説明、発表資料 |

## docsディレクトリ整理ルール

`docs/` は、製品仕様、旧メモ、移行前素材を分ける。

| 置き場所 | 役割 |
|---|---|
| `docs/製品パッケージ/` | 現在の製品仕様・正本に近い設計 |
| `docs/アーカイブ/` | 旧構想、旧発表メモ、参照頻度の低い検討資料 |
| `docs/構造持続理論ベースの新しい文明OSシミュレーション/` | AGI若者日本ドメインパック化前の素材置き場 |

ルール:

- 製品として今後読むものは `docs/製品パッケージ/` に置く。
- 過去検討として残すものは `docs/アーカイブ/` に置く。
- 実行入力候補TSVは、一時的に `docs/構造持続理論ベースの新しい文明OSシミュレーション/` に残す。
- 実行入力の正本は、最終的に `domain_packs/{pack_id}/data/` へ移す。
- 生成済みrowデータは `docs/` に置かない。

## ルートディレクトリ整理ルール

プロジェクト直下は肥大化させない。
直下に置くのは、入口として必要なものだけにする。

直下に残してよいもの:

| 種類 | 例 |
|---|---|
| プロジェクト入口 | `README.md`, `LICENSE.txt`, `requirements.txt` |
| 実行入口 | `main.py`, `scripts/` |
| 主要ソース | `sim_core/`, `domain_packs/`, 既存の旧2D実験用Pythonファイル |
| ドメイン設定 | `domain_packs/{pack_id}/domain.yaml`, `domain_packs/{pack_id}/scenarios/` |
| ドキュメント入口 | `docs/` |
| 可視化 | `visualization/` |
| 生成物置き場 | `outputs/`, `logs/` |

直下に増やさないもの:

| 種類 | 置き場所 |
|---|---|
| 旧2D空間実験の `config*.yaml` | `examples/spatial_demo/configs/` |
| `output_*` ディレクトリ | `outputs/spatial/` または `outputs/runs/` |
| `simulation_*.log` | `logs/spatial/` |
| rowデータ | `outputs/runs/{run_id}/` |
| 実行入力の正本 | `domain_packs/{pack_id}/data/` |
| 事前調査 | `research/{domain}/` |
| rawデータ | `data_sources/{source}/{snapshot_date}/` |

現在の移行ルール:

- 若者・現役世代シミュレーションの設定は `domain_packs/agi_youth_japan/domain.yaml` と `scenarios/*.yaml` に置く。
- 旧2D空間シミュレーションの設定は `examples/spatial_demo/configs/` に置く。
- 旧2D空間シミュレーションの出力は `outputs/spatial/` に置く。
- 文明OS/若者/国家モデルの生成rowは `outputs/runs/` に置く。
- ルート直下の `output/` は使わない。
- 旧 `world_demo_sim/` 系の単独世界デモは削除済み。国家モデルは `docs/構造持続理論ベースの新しい文明OSシミュレーション/国家モデル/` と `domain_packs/agi_youth_japan/` 側へ寄せる。

## サブエージェントレビュー反映

設計レビューでは、Python採用と `domain_packs / sim_core / model_adapters / outputs` 方向は妥当と判断された。

特に重要な指摘:

- 汎用化の中核は、2D空間実験ではなく、国家・日本状態・若者/現役エージェントの閉ループ実行側に置く。
- 2D空間実験は `examples/spatial_demo` として扱い、プロダクトcoreから切り離す。
- `generate(prompt) -> str` だけではプロダクト境界が弱いため、`ObservationModel.observe(request) -> ObservationRow` のような構造化レイヤーを追加する。
- TSVは編集用にはよいが、実行時は正規化済みオブジェクトに変換して検証する。
- 最初から全ドメインを完全統一しようとせず、`agi_youth_japan` を第一級ドメインパックとして固めてから外挿する。

## Domain Pack Protocol

ドメインパックは、`domain.yaml` を入口にする。

基本ルール:

- 1パック = 1ディレクトリ
- 入口ファイル = `domain.yaml`
- 人間が迷わないように標準ファイル名は決める
- プログラムが迷わないように実行で使うファイルは `domain.yaml` に明記する
- 複数パターンのファイルは置いてよいが、正本は `domain.yaml` 側で選ぶ

## データライフサイクル別の置き場所

今後は、データを「何に使う状態か」で分ける。

```text
research/
  # 事前調査、出典メモ、論文/統計の整理、まだ実行入力ではないもの

data_sources/
  # 取得したrawデータ、ダウンロード元に近いスナップショット

data_working/
  # rawから実行用へ変換する途中の作業データ

domain_packs/
  # シミュレーション実行に使う正規化済み入力

outputs/runs/
  # 実行結果。rowデータ、raw response、manifest、audit

exports/
  # スプシ貼り付け、発表、動画、UI投入用に加工した成果物

docs/
  # 設計思想、仕様、説明資料。実行入力の正本は置かない
```

判断基準:

| 種類 | 置き場所 | 説明 |
|---|---|---|
| 事前調査メモ | `research/{domain}/` | アイデア、出典候補、論点、未整理メモ |
| 論文・統計の要約 | `research/{domain}/evidence_notes/` | 人間が読むための根拠整理 |
| 取得した元データ | `data_sources/{source_name}/{snapshot_date}/` | raw CSV/JSON/PDFなど。原則変更しない |
| raw取得ログ | `data_sources/{source_name}/{snapshot_date}/source_manifest.json` | URL、取得日、ライセンス、対象期間 |
| 変換途中データ | `data_working/{domain}/{job_id}/` | 正規化前、列名調整中、集計途中 |
| 変換スクリプト | `scripts/ingest/` または `sim_core/ingestion/` | rawからdomain pack用TSVへ変換 |
| 実行入力データ | `domain_packs/{pack_id}/data/` | シミュレーションが読む正本 |
| 実行設定 | `domain_packs/{pack_id}/domain.yaml` | 使用ファイル、シナリオ、プロンプトを指定 |
| シナリオ設定 | `domain_packs/{pack_id}/scenarios/` | baseline、policy_a、stressなど |
| プロンプトテンプレート | `domain_packs/{pack_id}/prompts/` | LLM観測用。実行入力の一部 |
| 生成rowデータ | `outputs/runs/{run_id}/` | agent_turns、state_turns、feedbackなど |
| LLM raw response | `outputs/runs/{run_id}/raw_responses/` | モデルの生出力。監査用 |
| 実行時入力スナップショット | `outputs/runs/{run_id}/input_snapshot/` | 実行に使ったdomain packを固定保存 |
| 実行manifest | `outputs/runs/{run_id}/manifest.json` | モデル、ステップ、入力、出力の記録 |
| 監査結果 | `outputs/runs/{run_id}/audit_report.md` | 欠損、矛盾、範囲外、注意点 |
| UI再生用加工 | `outputs/runs/{run_id}/viewer/` | future_emotion_mapなどが読む形 |
| スプシ貼り付け用 | `exports/spreadsheets/` | タブ区切り、説明表など |
| 発表用素材 | `exports/presentation/` | 画像、動画、スライド貼り付け用 |
| 設計書 | `docs/` | 実装方針、仕様、思想、発表説明 |

重要ルール:

- `domain_packs/` は実行入力の正本だけを置く。
- `research/` のデータを直接シミュレーションで読まない。
- `data_sources/` のrawデータは原則変更しない。
- `data_working/` は作業中なので、実行時の正本にしない。
- `outputs/runs/` は実行ごとに不変ログとして扱う。
- `exports/` は人間向け加工物なので、再実行の正本にしない。
- `docs/` は説明用であり、実行入力TSVの置き場にしない。

## 必須プロトコル

### 1. Agent Protocol

エージェントrowの必須列。

| 列 | 意味 |
|---|---|
| `agent_id` | エージェントID |
| `display_name` | 表示名 |
| `segment_id` | 分類コード |
| `age` | 年齢または世代 |
| `region` | 地域 |
| `role_status` | 在学、就業、所属、役割など |
| `resource_level` | 所得、資源、余力の分類 |
| `trust_in_institutions` | 制度信頼 |
| `self_efficacy` | 自己効力感 |
| `information_sensitivity` | 情報接触・SNS感受性 |
| `initial_emotion` | 初期主感情 |
| `initial_action_bias` | 初期行動傾向 |
| `population_weight` | 人口重み |
| `voice_weight` | 発信影響重み |

ドメイン固有列は追加してよい。
ただし、必須列を欠かしてはいけない。

### 2. Event Protocol

イベントは、結果を命令しない。
社会状況として記述する。

必須列:

| 列 | 意味 |
|---|---|
| `event_id` | イベントID |
| `event_type` | `intervention` / `background` / `reaction` |
| `name` | イベント名 |
| `start_step` | 開始ステップ |
| `duration_steps` | 継続ステップ |
| `target_segment` | 対象 |
| `intensity` | 強度 |
| `uncertainty` | 不確実性 |
| `description` | 状況説明 |
| `affected_state_variables` | 影響する状態変数 |
| `evidence_level` | 証拠レベル |

悪い例:

```text
若者の不安を上げる
```

よい例:

```text
AI自動化により、新卒採用の見通しが不透明化し、SNSで雇用不安の投稿が増える。
```

### 3. State Protocol

状態変数は、0-100などの範囲を持つ。

必須列:

| 列 | 意味 |
|---|---|
| `state_id` | 状態変数ID |
| `name` | 表示名 |
| `description` | 意味 |
| `min_value` | 最小値 |
| `max_value` | 最大値 |
| `initial_value` | 初期値 |
| `source` | 出典または仮定 |
| `updated_by` | どのイベント/フィードバックで変わるか |
| `affects` | どの感情/行動に効くか |

### 4. Observation Row Protocol

LLMが返す個人観測row。

必須列:

| 列 | 意味 |
|---|---|
| `step` | ステップ |
| `agent_id` | エージェントID |
| `evaluation` | 良好/中立/注意/危険など |
| `emotion` | 主感情 |
| `intensity` | 感情強度 |
| `pathway` | 未来経路開放度 |
| `support` | 構造支援度 |
| `action_category` | 行動カテゴリ |
| `action_detail` | 具体行動 |
| `thought` | 内心 |
| `private_talk` | 近い人との会話 |
| `social_post` | SNS発信 |
| `perceived_situation` | 本人が知覚した状況 |
| `reasoning_basis` | 反応根拠 |
| `memory_update` | 次ステップに残る記憶 |
| `carryover_concern` | 持ち越し懸念 |

### 5. Observation Model Protocol

Model Adapter は文字列生成を担当する。
Observation Model は、構造化された観測リクエストを作り、モデル応答を検証済みrowへ変換する。

```python
class ObservationRequest:
    step: int
    actor: dict
    current_state: dict
    active_events: list[dict]
    previous_observation: dict | None
    domain_context: dict


class ObservationModel:
    def observe(self, request: ObservationRequest) -> dict:
        ...
```

この層を入れる理由:

- runner がプロンプト文字列に直接依存しない
- LLM/API/CLI/ルールベースを差し替えやすい
- raw response と正規化rowを分けて保存できる
- 出力修復、再試行、監査を共通化できる

### 6. Feedback Protocol

個人行動を集団反応へ集約し、状態変数へ戻す。

```text
agent_turns.tsv
  -> action_category集計
  -> population_weight / voice_weight適用
  -> feedback_channels.tsvで状態変数へ変換
  -> state_turns.tsvへ反映
```

`feedback_channels.tsv` の必須列:

| 列 | 意味 |
|---|---|
| `feedback_id` | フィードバックID |
| `source_action_category` | 元になる行動 |
| `source_emotion` | 元になる感情、任意 |
| `target_state_id` | 影響先状態変数 |
| `direction` | `increase` / `decrease` |
| `coefficient` | 影響係数 |
| `delay_steps` | 遅延 |
| `cap` | 上限 |
| `rationale` | 理由 |
| `evidence_level` | 証拠レベル |

## UI/Hookオーバーライド

UIも他の入力と同じように、defaultを持ち、domain pack側で差し替える。

```text
sim_core/defaults/viewer/viewer_config.yaml
  -> 標準viewer設定

domain_packs/{pack_id}/viewer/viewer_config.yaml
  -> ドメイン固有viewer設定

scenarios/{scenario}.yaml
  -> シナリオごとのUI差分が必要なら上書き
```

`domain.yaml` では次のように指定する。

```yaml
viewer:
  viewer_id: future_emotion_map
  config: "${pack}/viewer/viewer_config.yaml"
```

UI以外の拡張処理は `hooks` で宣言する。
最初からPythonプラグインを暴走させるのではなく、まずは「どの段階に何を差し込むか」を `resolved_config` に残す。

Hook stage:

| stage | 役割 |
|---|---|
| `pre_run` | 実行前の初期化 |
| `pre_step` | 各ステップ前の処理 |
| `pre_observation` | LLM観測前の入力加工 |
| `post_observation` | LLM観測後のrow修復・正規化 |
| `aggregate` | 個人rowから集団反応を作る |
| `feedback` | 集団反応を状態へ戻す |
| `post_step` | 各ステップ後の処理 |
| `export_viewer` | UI再生用データへ変換 |
| `audit` | 監査処理 |

例:

```yaml
hooks:
  export_viewer:
    - id: future_emotion_map_export
      enabled: false
      module: visualization.future_emotion_map
      function: export_viewer
      config:
        viewer_id: future_emotion_map
```

当面は `enabled: false` の宣言から始める。
実行器が対応した段階で `enabled: true` にし、module/functionをimportして実行する。

この設計により、UI、集約、フィードバック、監査、viewer exportを、ドメインパックやシナリオごとに差し替えられる。

## Schema Validation 方針

最初は Python 標準ライブラリ + PyYAML + dataclasses で始める。
ただし、プロダクト化する段階では `pydantic` または `jsonschema` の導入を検討する。

段階:

| 段階 | 方針 |
|---|---|
| Hackathon | dataclasses + 手書きvalidation |
| Prototype | dataclasses + schema定義を集約 |
| Product | pydantic/jsonschemaで入力とrowを厳格検証 |

重要なのは、TSVを直接信じないこと。
TSV/YAMLをロードしたあと、必ず正規化済みオブジェクトへ変換し、必須列、型、ID参照、値域を検証する。

## 監査Protocol

監査は実行後の必須工程にする。

最低限チェックするもの:

- domain pack の必須ファイルがある
- 必須列がある
- ID参照が壊れていない
- ステップ数が揃っている
- 各ステップに対象エージェントが揃っている
- 状態変数が範囲外になっていない
- 全員が同じ反応になっていない
- 感情と行動と理由が矛盾していない
- イベントが不足していない
- 出典レベルEの値が意思決定指標に過剰に効いていない

監査出力:

```text
audit_report.md
audit_errors.tsv
audit_warnings.tsv
```

## 最初に実装する最小単位

いきなり全エンジンを作り直さない。
最初はこの3つだけでよい。

```text

sim_core/schemas.py
sim_core/audit.py
```

これでできること:

- domain pack を読み込む
- 必須ファイルを検証する
- 必須列を検証する
- ID参照を検証する
- 既存TSVがプロダクト入力として使えるか判定する

その後に runner と model adapter を移す。

## 過剰設計を避けるルール

最初からやりすぎない。

まだやらないもの:

- Web API化
- DB化
- GUIでのdomain pack編集
- 複雑なプラグイン機構
- Pydantic等の重い依存追加
- 完全な型安全
- 全ドメイン共通の完璧な抽象化

まずは、TSV/YAMLを読み、検証し、既存の実行器へ渡せる状態を作る。
Python標準ライブラリ + PyYAML で十分に始められる。

ただし、意思決定補助プロダクトへ進める段階では、pydantic/jsonschemaなどの明示的なスキーマ検証を入れる。

## 判断

このまま実装できる。

ただし、いきなり既存スクリプトを全部置き換えるのではなく、まずは domain pack の配置と validation から始めるのがよい。
