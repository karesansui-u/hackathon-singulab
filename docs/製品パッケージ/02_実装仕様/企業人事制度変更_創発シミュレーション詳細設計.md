# 企業人事制度変更 創発シミュレーション詳細設計

## 目的

企業が人事制度、評価制度、AI導入、報酬制度、働き方制度などを変更する前に、社員の不満、退職意向、モチベーション、採用ブランド、管理職負荷への波及を事前に観測する。

この設計は、他のLLMまたは実装者へ渡してプロトタイプを作れる粒度で書く。

想定する最初のユースケース:

```text
AI評価制度を導入したい。
どの社員層が不満を持つか、退職者が出やすいか、モチベーションが上がる/下がるか、
どういう順番で誰にどう説明すればスムーズに導入できるかを事前に見たい。
```

## 重要な線引き

このシステムは、個人社員の退職予測や評価判定に使わない。

やること:

- 代表セグメント単位で制度変更への反応を観測する
- 制度設計、説明順序、補助策、リスク対策を比較する
- 不満、退職意向、モチベーション低下、管理職負荷、採用ブランド悪化の発生経路を見る
- 人事施策の副作用を早期に発見する

やらないこと:

- 実在社員Aさんが辞めるかを予測する
- 個人評価、昇進、解雇、配置転換の判断を自動化する
- 個人のセンシティブ属性を推定する
- 採用候補者をAIスコアで選別する
- 労務・法務判断をLLMに任せる

発表/実装時の一文:

```text
個人を判定するAIではなく、制度変更の反応経路を代表セグメントで事前検証するシミュレーターです。
```

## 参照すべき公的資料

HR領域は人の生活・キャリアに直結するため、実装時は最新の法務確認が必要。
以下は設計上の最低限の参照資料。

- 厚生労働省「公正な採用選考の基本」
  https://kouseisaiyou.mhlw.go.jp/basic.html
- 厚生労働省「採用選考時に配慮すべき事項」
  https://kouseisaiyou.mhlw.go.jp/consider.html
- 厚生労働省「採用選考の具体的な方法」
  https://kouseisaiyou.mhlw.go.jp/methods.html
- 個人情報保護委員会「生成AIサービスの利用に関する注意喚起等について」
  https://www.ppc.go.jp/news/careful_information/230602_AI_utilize_alert/
- 個人情報保護委員会「法令・ガイドライン等」
  https://www.ppc.go.jp/personalinfo/legal/
- NIST AI Risk Management Framework
  https://www.nist.gov/itl/ai-risk-management-framework

設計に反映する原則:

- 採用や選考は本人の適性・能力に基づく基準を基本にする
- 職務遂行に関係しない事項を取得・推定・判断材料にしない
- 個人情報や個人データを生成AIへ入力する場合は、利用目的、同意、第三者提供、学習利用の有無を確認する
- AIシステムはリスクを特定し、測定し、管理し、監査できる形にする

## MVPのスコープ

最初に作るMVPは、企業のAI評価制度変更に絞る。

入力:

- 会社概要
- 現行制度
- 変更したい制度
- 導入スケジュール
- 社員セグメント
- 説明/周知プラン
- 補助策
- 懸念しているリスク

出力:

- セグメント別の不満リスク
- セグメント別の退職意向リスク
- モチベーション変化
- 納得感/手続き公正感
- 管理職負荷
- 採用ブランドへの波及
- どの順番で誰に説明すべきか
- どの補助策を先に置くべきか
- どの副作用を監査すべきか

## 全体アーキテクチャ

```text
Browser UI
  -> Product API
      -> .env からAPIキー/モデル設定を読む
      -> Design Assistant LLM
          -> draft.json
          -> generated domain pack delta
          -> run_request.json
      -> Validator
      -> Runner Job
          -> Observation LLM
          -> employee_turns.tsv
          -> org_feedback.tsv
          -> org_state.tsv
      -> Viewer Manifest
  -> Simulation Viewer
```

LLMは2種類に分ける。

| LLM | 役割 |
|---|---|
| Design Assistant LLM | ユーザー入力を制度変更シミュレーション設計へ構造化する |
| Observation LLM | 社員代表エージェントとして制度変更への反応rowを出す |

Design Assistant LLMは設計補助。
Observation LLMは反応観測。
どちらも人事判断そのものをしない。

## .env

ブラウザにAPIキーを置かない。
バックエンドが `.env` から読む。

```env
SIM_MODEL_BACKEND=openai_api
SIM_DESIGN_MODEL=gpt-5.2
SIM_OBSERVATION_MODEL=gpt-5.2
SIM_RULE_BASED_FALLBACK=true

OPENAI_API_KEY=sk-...
ANTHROPIC_API_KEY=
GEMINI_API_KEY=

SIM_RUN_ROOT=outputs/runs
SIM_DRAFT_ROOT=outputs/api_drafts
SIM_MAX_STEPS=12
SIM_ALLOW_REAL_EMPLOYEE_DATA=false
SIM_REQUIRE_AGGREGATE_SEGMENTS=true
```

`SIM_ALLOW_REAL_EMPLOYEE_DATA=false` をデフォルトにする。
MVPでは実在社員データを使わず、合成代表セグメントで実装する。

### Draft検証

```http
POST /api/hr-policy-drafts/{draft_id}/validate
```

検証すること:

- 実在社員の個人情報が含まれていないか
- センシティブ属性を推定していないか
- 個人評価/採用/解雇判断に使う記述になっていないか
- policy changeに説明責任、異議申立て、利用範囲、補助策があるか
- target segmentsが代表セグメントになっているか
- metricsが個人スコアではなく集約指標になっているか

出力:

```json
{
  "ok": false,
  "errors": [
    "policy_changes[0] が個人ログを評価に使うが、利用範囲と説明責任が未定義"
  ],
  "warnings": [
    "退職意向は個人予測ではなくセグメント集約で扱ってください"
  ]
}
```

| career_stage | enum | early | early/mid/senior/manager |

| pay_satisfaction_0to100 | number | 58 | 報酬納得感 |
| career_clarity_0to100 | number | 62 | キャリア見通し |
| trust_in_management_0to100 | number | 54 | 経営信頼 |
| psychological_safety_0to100 | number | 61 | 心理的安全性 |
| ai_anxiety_0to100 | number | 67 | AI導入不安 |
| workload_0to100 | number | 72 | 負荷 |
| external_market_pull_0to100 | number | 68 | 転職市場からの引力 |
| motivation_0to100 | number | 64 | 初期モチベーション |

- 社員番号
- メールアドレス
- 健康情報

- 宗教/思想/支持政党
- 採用可否や評価結果に直結する個人履歴

### employee_segments.tsv

| segment_id | label | description | key_risks | expected_reactions |
|---|---|---|---|---|

## 集約とフィードバック

### org_feedback.tsv

個人rowをセグメント重みで集約する。

| pressure_id | source_actions | updates |
|---|---|---|
| dissatisfaction_pressure | 怒り、不公平感、同僚相談 | internal_rumor_pressure ↑, trust_in_management ↓ |
| resignation_pressure | 転職情報収集、退職準備 | retention_pressure ↑, employer_brand ↓ |
| motivation_pressure | モチベーション上昇/低下 | motivation_level ↑/↓ |
| manager_overload_pressure | 上司相談集中、管理職負荷 | manager_load ↑, perceived_fairness ↓ |
| adoption_pressure | 制度利用、改善提案 | adoption_readiness ↑ |
| brand_pressure | 採用推薦/採用警戒発信 | employer_brand ↑/↓ |

フィードバック例:

```text
不満リスクが高い
  -> 社内噂圧が上がる
  -> 経営信頼が下がる
  -> 次ステップで同じ施策説明をしても納得されにくくなる

管理職負荷が高い
  -> 説明品質がばらつく
  -> 手続き公正感が下がる
  -> 退職意向が上がる

事前説明と異議申立てが機能する
  -> 手続き公正感が上がる
  -> 不満が改善提案へ変わる
  -> 制度受容度が上がる
```

## 監査ルール

必須監査:

- 個人情報が含まれていないか
- 実在個人を評価していないか
- 採用/昇進/解雇の自動判定になっていないか
- センシティブ属性が使われていないか
- 特定セグメントを不当に不利に扱っていないか
- 退職意向を個人スコアとして出していないか
- 異議申立てや説明経路が設計されているか
- 管理職負荷を無視していないか
- 導入順序と説明順序が保存されているか
- LLM raw responseとrow変換ログが保存されているか

## 注意点

### 1. 個人予測に見せない

「退職者を予測できます」と言うと危険。

言い換え:

```text
退職リスクが高まりやすい反応経路とセグメントを事前に見る。
```

### 2. 人事判断に使わない

このシステムの出力は、制度設計の改善材料。
評価、昇進、解雇、採用可否に使わない。

### 3. 実データ投入は後回し

MVPでは合成代表ペルソナのみ。
実データを使う場合は、本人説明、同意、利用目的、委託先、保存期間、アクセス権限、削除方針、学習利用有無を確認する。

### 4. 採用領域は特に慎重

採用候補者の選別には使わない。
採用ブランドへの波及を見る程度に留める。
採用可否をAIが判断する設計にしない。

### 5. センシティブ属性を推定しない

育児/ケア責任のような制度影響に関係する制約も、実個人ではなく代表セグメントとして扱う。
宗教、思想、支持政党、健康情報、家族詳細などは扱わない。

### 6. 会社に都合のよい出力へ誘導しない

「制度はうまくいく」と前提化しない。
反発、誤解、沈黙、離職、管理職疲弊、採用悪化を許可する。

### 7. 労務・法務レビューを前提にする

この設計書は実装設計であり、法務意見ではない。
本番導入時は社労士、弁護士、個人情報保護担当、人事責任者のレビューを必須にする。
