# 高品質なドメインパックの作り方

## 目的

この文書は、AGI時代の若者シミュレーションだけでなく、企業、行政、学校、国家、地域など、別テーマでも同じ品質の「施策反応・波及シミュレーション」を作るための設計ルールである。

プロダクトとして重要なのは、毎回LLMに自由作文させることではない。
テーマごとに必要な情報、データ、辞書、評価軸、検証方法をドメインパックとして揃え、Simulation Core に渡すことで、再現性のある創発観測を行うことである。

```text
Simulation Core
  -> 共通の実行基盤

Domain Pack
  -> テーマ固有の現実・制度・人間・評価軸
```

## ドメインパックとは何か

ドメインパックは、特定テーマをシミュレーション可能にするための入力セットである。

たとえば今回なら、テーマは「AGI時代に、日本の若者と現役世代の未来感情・行動がどう変わるか」である。
企業なら「AI導入や評価制度変更で、社員の納得感、離職、協力、学習意欲がどう変わるか」になる。

ドメインパックに含めるもの:

- 何を試したいか
- 誰が影響を受けるか
- どの状態変数を見るか
- どの感情・認知を観測するか
- どの行動を観測するか
- どんな施策・イベントを入れるか
- どんな波及と副作用を見るか
- どのデータや仮定を根拠にするか
- どの指標で比較するか

## 品質を決める要素

高品質なシミュレーションは、プロンプトだけでは作れない。
品質は、次の掛け算で決まる。

```text
品質 =
  問いの明確さ
  × エージェント設計の妥当性
  × 現実データの接続
  × イベント/施策の現実性
  × 感情・行動辞書の適切さ
  × 波及チャネルの設計
  × フィードバックの設計
  × 監査可能性
```

プロンプトは重要だが、プロンプトは観測レンズである。
現実データ、対象集団、制度制約、評価軸の代替にはならない。

## 推奨ファイル構成

テーマごとに、最低限これくらいのファイルを持つと品質が安定する。

```text
domain_pack/
  domain_definition.md
  agents.tsv
  agent_segments.tsv
  state_variables.tsv
  interventions.tsv
  events.tsv
  emotion_dictionary.tsv
  action_dictionary.tsv
  perception_channels.tsv
  feedback_channels.tsv
  evaluation_metrics.tsv
  evidence_map.tsv
  assumptions.md
  prompt_context.md
  validation_plan.md
```

## 各ファイルの役割

| ファイル | 役割 |
|---|---|
| `domain_definition.md` | 何を検証するか、誰の意思決定に使うかを定義する |
| `agents.tsv` | 代表エージェントの属性、初期状態、重みを持つ |
| `agent_segments.tsv` | エージェント分類の意味を定義する |
| `state_variables.tsv` | 社会・組織・制度の状態変数を定義する |
| `interventions.tsv` | 試したい施策・制度変更・アクションを定義する |
| `events.tsv` | 背景イベント、世界イベント、組織内イベントを定義する |
| `emotion_dictionary.tsv` | 観測する感情・評価分類を定義する |
| `action_dictionary.tsv` | 観測する行動カテゴリを定義する |
| `perception_channels.tsv` | 情報が誰にどう届くかを定義する |
| `feedback_channels.tsv` | 個人反応が系全体へどう戻るかを定義する |
| `evaluation_metrics.tsv` | 施策比較に使う指標を定義する |
| `evidence_map.tsv` | データ、出典、仮定、信頼度を管理する |
| `assumptions.md` | 仮定、割り切り、未検証点を記録する |
| `prompt_context.md` | LLMに渡す背景情報を、人間が読める形で管理する |
| `validation_plan.md` | 監査、感度分析、複数回実行の計画を定義する |

## 1. 問いを固定する

最初に固定すべきなのは、データではなく問いである。

悪い問い:

- この制度はよいか
- 若者は希望を持てるか
- 会社はよくなるか

よい問い:

- 住宅支援を導入したとき、若者、子育て世帯、非対象者の感情と行動はどう分岐するか
- AI評価制度を導入したとき、若手、中堅、管理職、育児中社員の納得感、反発、離職意向はどう変わるか
- AGI時代の雇用不安が高まる中で、構造支援策が希望、撤退、連帯、子ども意向にどう効くか

問いには、最低限これを含める。

- 検証したい施策/変化
- 対象集団
- 観測したい感情
- 観測したい行動
- 見たい副作用
- 比較対象
- 時間軸
- 意思決定者

## 2. 構造持続理論レイヤーを入れる

構造持続理論は、単なる感情分類ではない。
見るべきなのは、構造が続く条件と、壊れたときの修復経路である。

ドメインパックでは、次の問いを必ず持つ。

| 観点 | 問い |
|---|---|
| 維持条件 | その構造を保つために何が必要か |
| 修復経路 | 壊れたときに直す経路があるか |
| 役割経路 | 人が自分の役割を見つけ直せるか |
| 資源循環 | お金、人、時間、情報、信頼が循環しているか |
| 制度信頼 | 制度が頼れるものとして知覚されているか |
| 次世代継承 | 次の世代に渡したいと思えるか |
| 代替不能性 | 失われると戻しにくいものは何か |

今回の若者テーマでは、構造持続理論レイヤーは次のように効く。

- 希望指数だけでなく、未来経路が残っているかを見る
- 子ども意向だけでなく、次世代を迎える構造条件があるかを見る
- 雇用だけでなく、役割を再獲得する経路があるかを見る
- 支援金だけでなく、修復可能性と制度信頼が残っているかを見る

## 3. エージェントを設計する

エージェントは「適当に30人置く」のではなく、対象集団の縮図として置く。

必須項目:

- ID
- 氏名/ラベル
- 分類コード
- 年齢/世代
- 地域
- 所得/資源制約
- 所属/雇用/役割
- 住居/生活基盤
- ケア責任
- 初期感情
- 初期行動傾向
- 制度信頼
- 自己効力感
- 情報接触傾向
- 人口重み
- 発信影響重み

エージェント設計で避けること:

- 平均的な人だけを置く
- 影響を受けやすい少数派を消す
- 全員に同じ情報を届かせる
- 全員に同じ合理性を仮定する
- 名前や属性だけで、生活制約がない

よいエージェントは、同じイベントを見ても反応が分岐する。

## 4. 状態変数を設計する

状態変数は、感情そのものではなく、感情や行動の背景になる環境である。

例:

| 状態変数 | 意味 |
|---|---|
| 雇用不確実性 | 将来の仕事・収入への不安定さ |
| 生活コスト圧 | 家賃、物価、教育費、医療費などの圧力 |
| 制度信頼 | 政府、会社、学校、地域制度への信頼 |
| 修復経路密度 | 困ったときに戻れる経路の多さ |
| 役割経路開放度 | 新しい役割を獲得できる見込み |
| 情報過敏圧 | SNSやニュースで不安が増幅する度合い |
| 連帯資本 | 一人ではなく共同で乗り切れる感覚の土台 |
| 構造支援度 | 制度・組織・地域が生活を支える実感 |

状態変数には、必ず次を持たせる。

- 0-100などの範囲
- 初期値
- 出典または仮定
- どのイベントで変わるか
- どの感情/行動に効くか
- 次ステップへどう持ち越すか

## 5. 施策とイベントを分ける

施策とイベントは分けて考える。

| 種類 | 意味 | 例 |
|---|---|---|
| 施策 | 意思決定者が打つ介入 | 給付、制度変更、AI導入、教育支援 |
| 背景イベント | 意思決定者が直接制御できない変化 | 景気変動、災害、国際緊張、技術事故 |
| 反応イベント | 人々の行動から生まれる二次現象 | 抗議、離職増、制度利用急増、連帯活動 |

施策には、成功条件だけでなく失敗条件も入れる。

- 対象者に届くか
- 非対象者がどう受け取るか
- 申請負荷が高すぎないか
- 周知が十分か
- 予算や人員が足りるか
- 遅れて効くのか
- 副作用がどこに出るか

イベントには、結果を命令しない。
「不安を上げるイベント」ではなく、「生活コストが上がり、情報環境で不安が拡散しやすい状況」として書く。

## 6. 感情辞書と行動辞書を分ける

感情と行動を混ぜると、シミュレーションの解像度が落ちる。

感情:

- 不安
- 怒り
- 裏切られ感
- 喪失感
- 絶望
- 諦念
- 平静
- 安心
- 希望
- 連帯感

行動:

- 静観
- 情報収集
- 相談
- 生活防衛
- 回避・縮小
- 学習・就活
- 制度利用
- 参加・連帯
- 抗議・発信
- ケア継続
- 撤退

同じ感情でも、行動は分岐する。

例:

- 怒り -> 抗議・発信
- 怒り -> 制度利用
- 怒り -> 離脱
- 不安 -> 情報収集
- 不安 -> 生活防衛
- 不安 -> 回避
- 希望 -> 学習
- 希望 -> 参加・連帯

ここが創発観測の重要部分である。

## 7. 情報接触を設計する

人は同じ現実を見ていない。
どの情報が、誰に、どの強度で届くかを設計する。

見るべきチャネル:

- SNS
- 友人/家族
- 職場/学校
- ニュース
- 行政/会社/学校からの公式説明
- 専門家情報
- 地域コミュニティ
- 当事者経験

情報接触を入れると、同じ施策でも反応が分岐する。

- 制度信頼が高い人は公式説明を受け取りやすい
- SNS感受性が高い人は不安・怒りが増幅しやすい
- ケア責任がある人は生活影響を優先して知覚する
- 余裕がない人は制度があっても調べられない

## 8. フィードバックを設計する

創発観測装置として重要なのは、個人反応を眺めるだけで終わらせないこと。
反応を次の状態へ戻す。

```text
個人の感情・行動
  -> 集団反応
  -> 社会/組織状態の変化
  -> 次ステップの知覚環境
  -> 次の感情・行動
```

フィードバック例:

| 集団反応 | 次に効く状態 |
|---|---|
| 撤退が増える | 雇用不確実性、社会参加低下、制度信頼低下 |
| 抗議が増える | 制度要求圧、SNS不安、政策修正圧 |
| 制度利用が増える | 財政圧、制度認知、支援実感 |
| 学習移行が増える | 役割経路開放度、雇用不確実性低下 |
| 連帯が増える | 連帯資本、構造支援度、孤立感低下 |
| 情報過敏が増える | SNS不安、怒り、疲弊、回避 |

ここを設計しないと、単発の感想生成で終わる。

## 9. 証拠と仮定を分ける

すべてを実データで埋める必要はない。
ただし、実データ、先行研究、仮説、創作を混ぜてはいけない。

証拠レベルを明示する。

| レベル | 意味 |
|---|---|
| A | 公的統計・実測データ |
| B | 調査・先行研究 |
| C | 歴史事例・類似ケース |
| D | 専門家仮説・設計仮説 |
| E | デモ用の仮置き |

各値には、できれば次を持たせる。

- 出典
- 年次
- 対象範囲
- 使い方
- 不確実性
- 更新予定

意思決定に使うなら、Eの比率を下げる。
ハッカソンデモなら、Eがあってもよいが、Eであることを隠さない。

## 10. プロンプトでできること、できないこと

プロンプトでできること:

- 役割を人物/組織/国家モデルとして保つ
- 命令ではなく情報入力として扱わせる
- 感情と行動を分けて出させる
- 反応根拠を説明させる
- 内心、会話、SNS発信を分ける
- 出力形式をrowに揃える
- 望ましい結論に寄せないよう制約する

プロンプトではできないこと:

- 存在しない現実データを補う
- 人口構成の偏りを自然に直す
- 施策の制度制約を勝手に正確化する
- 未来イベントの発生確率を保証する
- 社会科学的妥当性を自動で担保する
- 1回の実行で結論を確定する

プロンプトは品質を上げるが、品質保証の全部ではない。
ドメインパックのデータ設計、証拠管理、監査が必要である。

## 11. 実行シナリオを作る

高品質なドメインパックでは、1つの未来だけを作らない。
最低限、比較用シナリオを持つ。

| シナリオ | 意味 |
|---|---|
| ベースライン | 施策なし/現状延長 |
| 施策A | 主要施策を導入 |
| 施策B | 別案を導入 |
| ストレス | 悪化イベントが重なる |
| 緩和 | 支援や連帯が効く |

見るべきなのは、単一の結果ではなく差分である。

- 施策なしと比べて誰が改善したか
- 誰に副作用が出たか
- 何ステップ遅れて効いたか
- 感情は改善したが行動は変わらない層があるか
- 短期では悪化するが長期では改善するか

## 12. 監査する

生成後は、必ず監査する。

監査項目:

- 必要なステップが揃っているか
- 全エージェントが出力されているか
- イベントが不足していないか
- 状態変数が固定されすぎていないか
- 全員が同じ方向に動いていないか
- 発表に都合よすぎる結果になっていないか
- 感情、行動、根拠が矛盾していないか
- 副作用が出るべき場面で消えていないか
- 人口重みと集約指標が一致しているか
- 施策A/B比較ができる形になっているか

## 品質レベル

用途ごとに、求める品質を分ける。

| レベル | 用途 | 必要条件 |
|---|---|---|
| Prototype | アイデア検証 | 仮置きエージェント、簡易イベント、少数ステップ |
| Hackathon | 発表デモ | UI再生、説明可能row、最低限の証拠管理 |
| Research | 仮説検証 | 複数シナリオ、複数回実行、出典管理、監査 |
| Decision Support | 意思決定補助 | 実データ接続、専門家レビュー、感度分析、比較レポート |

今回のハッカソンでは、Hackathon から Research の入口を目指すのが現実的である。
「本番意思決定にそのまま使える」と言い切るより、「意思決定前に反応経路と副作用を洗い出す」と言うほうが強い。

## 作成手順

新しいドメインパックを作るときは、この順番で作る。

1. テーマと意思決定用途を定義する
2. 比較したい施策/シナリオを決める
3. 影響を受ける主体を分類する
4. 代表エージェントと人口重みを作る
5. 状態変数を定義する
6. 感情辞書と行動辞書を選ぶ/調整する
7. 施策・背景イベント・反応イベントを分けて作る
8. 情報接触チャネルを設計する
9. フィードバックチャネルを設計する
10. 証拠と仮定を evidence_map に分けて記録する
11. LLM観測プロンプトへ接続する
12. 小規模に実行する
13. 監査する
14. シナリオ比較を作る
15. UIで再生する

## 最小合格ライン

高品質なドメインパックとして最低限満たしたい条件:

- 問いが明確である
- 比較対象がある
- エージェント分類の意味が読める
- エージェントに人口重みがある
- 感情と行動が分かれている
- 施策と背景イベントが分かれている
- 情報接触の差がある
- 個人反応が次ステップへ戻る
- 出典と仮定が分かれている
- 生成rowの理由が読める
- 監査できる

これを満たすと、テーマが変わっても一定以上の品質でシミュレーションできる。

## 一文で言うと

高品質なドメインパックとは、LLMに任せるための設定集ではなく、現実の構造、対象集団、施策、情報環境、反応、波及、検証方法を、LLMが観測可能な形に翻訳したもの。
